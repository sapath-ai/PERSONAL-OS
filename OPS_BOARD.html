This section defines what must be interview-ready for AI Engineer, ML Engineer, AI Systems and Research roles. It is preparation guidance, not an application tracker.

LOOP 01 · CODING

DSA + implementation

Target: solve unfamiliar problems cleanly under time pressure.

  • Arrays, strings, hashing and two pointers
  • Stacks, queues, linked lists
  • Trees, heaps and graphs
  • Binary search and sorting
  • Recursion, backtracking and dynamic programming
  • Intervals, greedy and prefix/sweep techniques
  • Complexity analysis
  • Edge-case discipline
  • Readable implementation
  • Verbal problem decomposition
READY WHEN

You can derive an approach, state complexity, code it cleanly, test edge cases and recover when the first approach fails.

LOOP 02 · ML / AI FUNDAMENTALS

Conceptual depth

Target: explain why a method works, when it fails and what you would change.

  • Probability and statistics
  • Bias/variance and generalization
  • Optimization and losses
  • Regularization
  • CNNs and transformers
  • Attention and embeddings
  • Fine-tuning and inference
  • RAG and retrieval
  • Evaluation and experiment design
  • Data leakage and failure analysis
READY WHEN

You can answer why, compare alternatives, diagnose a failure and connect theory to an implementation you have actually built.

LOOP 03 · SYSTEM DESIGN

Production AI architecture

Target: design a reliable AI system from requirements to operations.

  • Requirements and SLOs
  • API and service boundaries
  • Data and storage design
  • Model selection/routing
  • RAG retrieval architecture
  • Caching and batching
  • Queues and concurrency
  • Observability
  • Security and access control
  • Latency, cost and reliability trade-offs
READY WHEN

You can state assumptions, draw the architecture, identify bottlenecks, explain failure modes and justify trade-offs quantitatively.

LOOP 04 · PROJECT / RESEARCH DEFENCE

Can you defend your work?

Target: make your strongest projects impossible to expose as shallow portfolio pieces.

  • 90-second project pitch
  • 10-minute architecture deep dive
  • Problem and motivation
  • Baseline selection
  • Experimental design
  • Ablation logic
  • Failure cases
  • Quantitative results
  • Limitations
  • Next experiment / next engineering step
READY WHEN

You can defend every major decision, reproduce the reasoning behind your results and openly explain what did not work.

UPDATE 07 · PROJECT PROOF SYSTEM · 2026/27
YOUR PROJECTS ARE YOUR TECHNICAL WITNESSES

Build fewer projects. Make each one impossible to dismiss.

A project only counts as career proof when another engineer or researcher can inspect it, reproduce the result, challenge the assumptions and understand what you learned.

01 · PROBLEM

Why does this need to exist?

State the user/research problem, constraints, baseline and why the problem is technically non-trivial.

02 · DESIGN

Why this architecture?

Show the architecture, interfaces, data flow, model choices and alternatives rejected with reasons.

03 · IMPLEMENTATION

Can it actually run?

Provide reproducible setup, clean code, tests, configuration, dependency control and a working execution path.

04 · MEASUREMENT

What did you prove?

Define metrics, establish baselines, benchmark quality/performance/cost and report results without cherry-picking.

05 · FAILURE

Where does it break?

Document failure cases, error taxonomy, bottlenecks, invalid assumptions and what the system cannot currently guarantee.

06 · DEFENCE

Can you survive questions?

Prepare the 90-second pitch, 10-minute deep dive, architecture defence, trade-off answers and next-step proposal.

PROOF ARTIFACT STACK

Every serious project should leave a trail of evidence

REPOSITORY

Clean source tree, setup instructions, configuration, tests and meaningful commit history.

ARCHITECTURE

One readable system diagram showing components, interfaces, data/model flow and operational boundaries.

EXPERIMENTS

Baseline → intervention → ablation → result. Record seeds/configuration and explain deviations.

BENCHMARK

Use task-appropriate metrics plus latency, throughput, memory or cost where relevant.

FAILURE REPORT

Show what failed, how it was detected, why it happened and what mitigation was attempted.

TECHNICAL WRITE-UP

Problem, method, design decisions, results, limitations and next steps in concise technical language.

DEMO / REPRODUCTION

A reviewer should be able to run or inspect the core result without a private explanation from you.

INTERVIEW PACK

90-second pitch, architecture deep dive, five trade-offs, three failures and three next experiments.

FLAGSHIP PROJECT STANDARD

Four projects, four different kinds of proof

PRODUCTION GENAI

Must prove reliability, evaluation, observability, security, latency/cost and deployment—not merely a chatbot demo.

MEDICAL AI

Must prove scientific rigor: baselines, ablations, robustness, error analysis, reproducibility and limitations.

GPU / INFERENCE

Must prove performance engineering: profiling, bottleneck isolation, optimization iterations and quantitative before/after results.

PAPER REPRODUCTION

Must prove research discipline: faithful reproduction, deviation analysis, limitation identification and a meaningful extension.

PROJECT RED FLAGS
  • Tutorial clone with no original engineering decision
  • Benchmark without a baseline or methodology
  • Claims of "production-ready" without deployment or failure testing
  • Research result without ablations or reproducibility information
  • Architecture diagram that does not match the actual implementation
  • Repository that cannot be installed or understood by another engineer
  • Large tool stack used as a substitute for technical depth
PROJECT PROOF GATE

If an interviewer asks “Why this design?”, “What failed?”, “How did you measure it?”, “What would you change?”, or “Can I reproduce this?”, the project should already contain a defensible answer.

FUNDING IS PART OF THE TARGET, NOT AN AFTERTHOUGHT

Rank PhD opportunities by research fit + funding quality + admission mechanics.

Monthly stipend alone is a poor comparison. A serious target needs a funding class, funding certainty, tuition treatment, employment/student status, timing, obligations and research upside understood before it moves into the final application set.

FUNDING COMPARABILITY RULE

Never rank two offers by headline monthly cash alone. Compare gross vs net pay → tuition/fees → healthcare/insurance → housing/cost of living → employment status → funding duration → annual increases → teaching duties → service obligations → conference support → research freedom.

A · EMPLOYED DOCTORAL RESEARCHER

Salary model

Doctoral researcher is an employee and student. Salary, social contributions and employment benefits matter as much as the headline number. Typical of Swiss/European funded research positions.

B · FULL SCHOLARSHIP

Stipend model

Tuition may be waived or covered and the student receives a fixed stipend. Compare the stipend to local costs and check duration/renewal conditions.

C · SCHOLARSHIP + ASSISTANTSHIP

Mixed model

Funding can combine scholarship, research assistantship or teaching support. Confirm which component is guaranteed and for how long.

D · PROJECT / SUPERVISOR FUNDED

Position model

Funding depends on a funded project or supervisor-held grant. The relevant unit may recruit through a specific vacancy rather than a generic PhD application.

E · COMPETITIVE FUNDING

Funding after admission

Admission and funding can be separate decisions. A technically strong admission without a funding award is not equivalent to a funded PhD.

F · VERIFY

Do not assume

When the current official program page does not specify a universal funding model, mark it for verification rather than inserting an unsupported stipend claim.

UPDATE 05 · GATE INTERPRETATION

How to decide whether a tier is actually unlocked

A tier is unlocked by demonstrated capability. It is not unlocked by course completion, tool familiarity or inflated self-assessment.

HARD GATE

Every tier has a small set of non-negotiable capabilities. Missing one critical gate means the tier is not yet ready.

PROOF GATE

At least one artifact must demonstrate the capability under realistic constraints: code, benchmark, deployment, experiment or research output.

DEFENCE GATE

You must be able to explain the artifact, its alternatives, failure modes, trade-offs and next improvements without relying on notes.

TRANSFER GATE

You should be able to apply the underlying principle to a new interview or system-design problem rather than reproducing a memorized solution.

RED FLAGS

Tutorial-copy projects, unverifiable benchmarks, tool-name stacking, notebook-only portfolios and projects whose architecture cannot be explained do not count as strong proof.

CEILING

The highest unlocked tier is the highest tier for which the core gates and proof bar are satisfied. Higher tiers remain targets, not claims.

PROGRESSION BLOCKERS

Common reasons a tier stays locked

ENTRY → PRODUCT

No deployed service, weak testing, no evaluation methodology, or inability to explain data/API decisions.

PRODUCT → HIGH-BAR

No measurable latency/cost/quality trade-offs, weak system design, or no evidence of operating under constraints.

HIGH-BAR → RESEARCH

Cannot formulate hypotheses, design controlled experiments, interpret failures or critique literature.

RESEARCH → ELITE

No differentiated contribution, weak reproducibility, shallow systems knowledge or inability to defend quantitative results.

UNLOCK RULE

A tier becomes credible only when its core skills + proof artifact + defence ability + transfer ability are all present. A higher tier is a target until those gates are met.

UPDATE 05 · ELIGIBILITY DEPTH

Baseline gate vs. stretch signal

The tier tells you what you must be able to demonstrate before applying. Stretch signals improve competitiveness but do not replace the baseline.

BASELINE GATE

Non-negotiable capability required to credibly target the tier. If it is missing, the correct action is to close the skill/proof gap rather than inflate the target.

PROOF ARTIFACT

A repository, deployed service, benchmark, experiment, paper reproduction, technical report or equivalent artifact that demonstrates the capability.

INTERVIEW DEFENCE

Explain implementation, assumptions, alternatives, failure modes, measurements and trade-offs under time pressure.

STRETCH SIGNAL

Open-source contribution, publication/preprint, difficult systems optimization, strong benchmark result or other differentiated public evidence.

DO NOT CONFUSE ELIGIBILITY WITH COMPETITIVENESS.

Meeting a tier's baseline means you have a credible reason to apply. It does not guarantee interviews, offers, funding or admission. Competitive selection depends on the applicant pool, role, institution and timing.
